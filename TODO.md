## Framework

1. **Empty the bootstrap scripts: build the host tools in place.** The goal is to remove almost
   every line of `utilities/bootstrap.*` and of the `dnf install` list of `Dockerfile`, leaving the
   host a compiler, a shell and little else: every other tool a build runs becomes a `:native`
   (or `:cross`) package the framework builds, as `lfs/perl5:native`, `lfs/Tcl:native`,
   `lfs/mdbook:native` and `lfs/libical:cross` already are. Known steps:
   - the wayland documentation still runs `dot` (graphviz), `xsltproc` and the docbook XSL style
     sheets of the host, and the `ical-glib-src-generator` of `lfs/libical:cross` links the host
     libxml2 (`graphviz`, `libxslt`, `docbook-style-xsl`, `libxml2-devel` in the lists):
     candidates for `lfs/graphviz:native`, native libxslt and docbook-xsl, an `lfs/libxml2:cross`
     variant;
   - the native perl lives outside the `PATH` of the builds (`${GLOBAL_TOOLCHAIN_PATH}/perl5`,
     only `lfs/openssl` uses it): serving every build with it, built before the autotools, lets
     the `perl-*` host packages go once it also carries the non core modules the builds use
     (`XML::Parser` for intltool);
   - the native Python of `setup_python` links the host `openssl-devel`, `libffi-devel`,
     `libuuid-devel`, `tcl-devel`, `tk-devel`: native builds of those libraries (openssl and Tcl
     already have one);
   - go through the remaining lines one by one (docbook-utils, docbook2X, asciidoc, texinfo,
     gtk-doc, help2man, swig, gperf, flex, pandoc, intltool, the `*-devel` packages) and either
     give the tool a native recipe or drop the feature that needs it.

## Recipes

2. **bind9 as a mesonninja recipe.** Pinned to 9.20.29 (autotools) because 9.21.x and the coming 9.22
   stable build with meson only. Moving on needs `BUILD_PROCESS=mesonninja`, the meson options in place
   of `--with-libsystemd` and `BUILD_CC`, and a way to build only the libraries for the `bootstrap`
   target (the autotools recipe sets `SUBDIRS = . lib` in `Makefile.in`).
3. **libclc for the target LLVM.** LLVM 23 builds libclc only as a runtime (`LLVM_ENABLE_RUNTIMES`),
   with the just built clang, which the cross build of `lfs/llvm` cannot execute; the recipe dropped
   it. Needed only if Mesa gets `-Dgallium-rusticl=true` (OpenCL): then either a native libclc build
   installed into the sysroot (the bitcode is target independent) or the runtimes cross machinery.
4. **librsvg gdk-pixbuf SVG loader.** The 2.63.0 meson recipe sets `-Dpixbuf-loader=disabled`. The
   `pixbufloader-svg` crate links `-lrsvg-2` through the uninstalled pc file of the build directory,
   whose `-L` path gets `PKG_CONFIG_SYSROOT_DIR` prepended ("cannot find -lrsvg-2"), and meson installs
   the loader into the sysroot path of `gdk_pixbuf_moduledir`. Ideas: a sysroot-free pkg-config lookup
   for the uninstalled file, or a postbuild copying `libpixbufloader_svg.so` into the staging directory,
   plus a postinstall running `gdk-pixbuf-query-loaders --update-cache` inside the chroot.
5. **nss.pc library directory.** The `nss.pc` generated by the BLFS standalone patch hardcodes
   `libdir=${prefix}/lib` and `-L${prefix}/lib`, while the libraries are installed in the multiarch
   directory (`lib/<triple>`). Poppler links anyway through the default search path of the toolchain;
   the file should carry `INSTALL_LIBDIR` and `INSTALL_LIBSUFFIX`.
6. **gdk-pixbuf glycin loader.** The 2.44.8 recipe sets `-Dglycin=disabled` (glycin is a Rust
   sandboxed image loader with no recipe) and keeps the classic loaders. Upstream is moving the
   loaders to glycin: a recipe will be needed when the classic ones go.
